# tron-vanity-gpu

GPU generator for Tron vanity addresses. Pick how the address starts, ends, or both — `TAnton…`, `…pump`,
`TSun…777` — and the GPU tries well over a billion keys per second until one fits.

**Up to ~1.8 billion keys/sec on an RTX 5080**: ~1.8 billion for prefixes, 1.4–1.75 billion for suffixes of
6+ characters, ~1.1 billion for short suffixes.
Keys are standard secp256k1 private keys and import into TronLink and other Tron wallets.

## Usage

```bash
tron_vanity -p Anton -n 1          # starts with TAnton (the leading T is added for you)
tron_vanity -s pump -n 10          # ends with pump
tron_vanity -m "TSun*777"          # starts with TSun and ends with 777
tron_vanity -s moon -s sun -i      # ends with moon OR sun, any letter case
tron_vanity --selftest             # check the GPU against the CPU reference
```

| Option | Meaning |
|---|---|
| `-p, --prefix P` | address starts with `P` (repeatable) |
| `-s, --suffix S` | address ends with `S` (repeatable) |
| `-m, --match P*S` | starts with `P` and ends with `S` (repeatable) |
| `-i, --ignore-case` | case-insensitive matching |
| `-n, --count N` | stop after `N` matches |
| `-o, --out FILE` | CSV file (default `tron_vanity_results.csv`) |
| `-d, --device N` | GPU index |
| `--bench SEC` | run `SEC` seconds and print the rate |
| `--selftest` | check GPU addresses and the matcher against the host reference |

Results go to a CSV file: `address,private_key` (64 hex characters). TronLink: *Import wallet → Private key*.
At start the program prints the odds (`1 in N keys`) and, while running, the expected time per match.

Every Tron address is 34 characters and starts with `T`; the second character is limited by the format, so some
prefixes are impossible — the program tells you. Base58 has no `0`, `O`, `I`, `l`.

## Performance

| Pattern length (after `T`) | Combinations | Average wait at ~1.6G keys/sec |
|---|---|---|
| 4 | 11.3 M | 0.01 seconds |
| 5 | 656 M | ~0.4 seconds |
| 6 | 38 G | ~25 seconds |
| 7 | 2.2 T | ~23 minutes |
| 8 | 128 T | ~22 hours |

Compared on the same RTX 5080 with ProVanity 1.1.2 (Tron suffix: 1.16 billion keys/sec; EVM benchmark:
1.63 billion), this is 20–50% faster on suffixes of 6+ characters and ~10% faster on prefixes.

The wait is geometric: you may get lucky in seconds, or it may take 2–3× the average.

## Installation

Pre-built binaries are on the [Releases](../../releases) page — one per GPU generation:
`tron_vanity_sm75` (RTX 20xx / GTX 16xx), `sm86` (RTX 30xx), `sm89` (RTX 40xx), `sm120` (RTX 50xx).

Build from source (CUDA ≥ 12.0, ≥ 12.8 for RTX 50xx; MSVC on Windows, GCC on Linux):

```bash
.\build.bat            # Windows, for the GPU in this machine (set SM_ARCH=sm_89 to override)
./build.sh             # Linux
```

## How it works

1. **Start keys.** Each GPU thread takes a random 256-bit scalar `k0` from ChaCha12 keyed with 32 bytes from the
   OS RNG (`BCryptGenRandom` / `/dev/urandom`) and computes `P0 = k0·G` once.
2. **Neighbour keys.** It then walks `k0 + j` with affine additions of precomputed `j·G`. 65 additions share one
   field inversion (Montgomery's trick), and every inverse serves both `P + jG` and `P − jG`, so a key costs about
   five field multiplications. After 4128 keys the thread takes a fresh random start.
3. **Field arithmetic.** secp256k1 on 8 × 32-bit limbs in PTX, Karatsuba multiplication, reduction with
   `2^256 ≡ 2^32 + 977`; generated by `tools/gen_secp.py`.
4. **Address.** `Keccak-256(X‖Y)` → `0x41 ‖ last 20 bytes` → double SHA-256 checksum → Base58. Prefixes are
   filtered on the top bits, no checksum needed. A suffix of K characters fixes `N mod 58^K` with
   `N = A·2^32 + checksum`, so the needed checksum follows from the address alone; for K ≥ 6 it is almost always
   ≥ 2^32 and the double SHA-256 is skipped (89% of keys for K = 6, 99.8% for K = 7). The few keys that still
   need it wait in a per-warp queue and are hashed 32 at a time with every lane busy.
5. **Check.** Every match is recomputed on the CPU with an independent implementation (plain modular arithmetic,
   Keccak, SHA-256) before it is written. `tools/tron_ref.py --verify file.csv` re-checks a CSV in pure Python.

## Security

- Keys come from the OS RNG through ChaCha12; there is no time- or counter-based seed (the flaw that broke
  Profanity).
- Neighbouring keys inside one 4128-key chunk differ by small offsets. Starts of different chunks are independent,
  so a private key you give away reveals nothing about addresses found in other chunks. If you sell or hand out
  addresses, generate each one in a separate run.
- No network access. The results CSV holds private keys in plain text — keep it safe and never commit it.
